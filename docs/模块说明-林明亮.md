# 模块说明：本地存储（2 号 林明亮）

## 1. 模块边界

| 项目 | 内容 |
| --- | --- |
| 负责文件 | `backend/app/storage.py`、`tests/backend/test_storage.py`、`examples/demo_records.json` |
| 不负责 | HTTP 解析（1、3、4 号）、参数校验（6 号）、统计计算（5 号）、界面（7—11 号） |
| 数据文件 | `data/records.json`，UTF-8 JSON，根节点是数组（README 6.1） |
| 依赖 | `backend/app/errors.py` 的 `StorageError`（1 号负责） |
| 被谁使用 | 3 号新增记录 `append_record`、4 号查询 `list_records`、5 号统计 `list_records`、1 号装配 `initialize` |

## 2. 公开接口

```python
JsonRecordStore(file_path)

initialize() -> None                  # 首次运行建目录 + 空数组；已有文件只校验不改写
list_records() -> list[dict]          # 每次重新读盘，返回副本
append_record(record: dict) -> dict   # 读—追加—写回整体加锁，落盘成功才返回
```

`record` 的字段与 README 6.1 一致：`id`（UUID 字符串）、`date`（`YYYY-MM-DD`）、`type`（`income`/`expense`）、`amount_cents`（整数分）、`category`、`note`、`created_at`（带时区的 ISO 8601）。`note` 缺失或为 `null` 时，存储层在写入与读取两侧都补成空字符串，避免前端插值显示成 "null"。

## 3. 四个必须守住的行为（也是本模块的验收点）

### 3.1 重启不丢数据

所有记录只经过本模块落盘，进程退出不需要额外 flush。`list_records()` 每次都重新读文件，而不是返回内存缓存，因此重启、外部编辑、另一个进程写入都能被读到。

### 3.2 损坏文件不会被当成空账本覆盖

`_read_all()` 在读取时校验：根节点必须是数组、每条记录字段齐全、`id` 是合法 UUID 且不重复、`date` 是真实日期、`amount_cents` 是正整数（单独排除 `bool`，因为 `True` 会被当成 1 分）、`created_at` 带时区。任一项不满足就抛 `StorageError`，**原文件字节不动**，启动时也不会写入 `[]`。

这是本模块最容易写错的地方：早期版本在 `initialize()` 里"文件解析失败就当空数组继续"，结果用户的账本被第一条新增记录覆盖成只有一条。现在的做法是先 `_read_all()` 校验，失败直接报错，提示用户检查或恢复备份。

### 3.3 写入是原子的

`_write_all()` 的顺序是：同目录 `tempfile.mkstemp` → 写入 → `flush()` + `os.fsync()` → `os.replace()` 覆盖正式文件。

- 临时文件必须与目标同目录，跨盘 `os.replace` 不是原子操作；
- 用 `os.replace` 而不是"先删除再写"，避免中途失败留下半个文件；
- 任何 `OSError` 都转成 `StorageError("...原文件未改动")`，`finally` 里清理临时文件。

测试用 `monkeypatch` 把 `os.replace` 改成抛异常，验证正式文件字节不变、临时文件被清理。

### 3.4 锁覆盖整个"读—改—写"

`append_record()` 的 `with self._lock:` 从 `_read_all()` 一直包到 `_write_all()`。如果只锁最后那次写入，两个并发请求会各自读到同一份旧数据，后写的覆盖先写的，直接丢一条记录。并发用例：8 个线程各追加 10 条，最终必须是 80 条且 id 全不重复。

## 5. 已知限制（演示时要能如实回答）

1. **只适用于单进程**。`threading.RLock` 只保证同一进程内线程安全；如果开两个后端进程指向同一个 JSON，会互相覆盖。README 8.2 已声明本设计针对本地单进程，换多进程/多用户必须重新评估（例如文件锁或 SQLite）。
2. **每次读取全量载入内存**。个人记账量级（几千条）没有问题，上万条以后应换成数据库；`filter_records` 也不做索引。
3. **没有 `save_all`**。这是故意的：业务模块拿到"整体覆盖"能力后容易写出 id 重复或金额非整数的记录。
4. **不支持编辑与删除**。README 14.3 的 PATCH/DELETE 需要在本模块增加 `update_record`/`delete_record` 原子操作，目前未实现。
5. **校验只针对文件完整性**，不判断类别是否与收支类型匹配（那属于 6 号 `validators` 的业务校验）；因此直接手改 JSON 可能写出"工资类型的餐饮支出"，接口层会拦住，存储层不会。

## 6. 演示时可以讲的三句话

- "金额全程用整数分，`0.10 + 0.20` 在账本里是 `10 + 20 = 30` 分，不经过浮点。"
- "写文件是临时文件 + fsync + `os.replace`，断电或写失败时正式文件仍是上一版完整内容。"
- "文件坏了我会报错并保留原文件，不会把它当成空账本——否则用户第一条新记录就把历史记录清空了。"
