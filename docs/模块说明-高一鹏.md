# 模块说明：查询筛选（4 号 高一鹏）

## 1. 模块边界

| 项目 | 内容 |
| --- | --- |
| 负责文件 | `backend/app/services/record_query.py`、`backend/app/routes/record_query.py`、`tests/backend/test_record_query.py`、`tests/backend/test_query_api.py` |
| 不负责 | 参数合法性判断（6 号 `validators`）、读文件（2 号 `storage`）、汇总统计（5 号）、界面（10 号） |
| 依赖 | `RecordFilter` / `parse_filters` / `parse_pagination`（6 号）、`record_store`（1、2 号）、`ValidationError`（1 号） |

## 2. 公开接口

```python
filter_records(records, filters) -> list[dict]       # 纯函数：只过滤，不排序、不分页
query_records(records, filters, *, limit, offset)     # 过滤 + 稳定排序 + 分页 + total
```

```http
GET /api/records?start_date=&end_date=&type=&category=&min_amount=&max_amount=&limit=&offset=
```

响应：`{"data": {"items": [...], "total": 3, "limit": 20, "offset": 0}}`。

## 3. 口径与实现要点

### 3.1 条件之间是 AND，未填写不参与筛选

`_matches()` 逐项判断，任何一项不满足立即返回 `False`。空字符串在 `validators.parse_filters` 里已视为未填写，所以 `?type=` 等于不筛类型。

### 3.2 日期与金额都含边界，且不自动交换

- 日期：`record_date < start_date → 不匹配`、`record_date > end_date → 不匹配`，等于时保留，因此起止当天都算。
- 金额：针对**单笔**金额，`min_amount_cents`、`max_amount_cents` 都含边界，也允许 0 作为边界。
- 开始日期晚于结束日期、最低金额高于最高金额 → 400，**不自动交换**：交换等于替用户猜意图，筛选结果会悄悄变。

### 3.3 日期比较用字符串而不解析

`date` 在存储里已是严格 `YYYY-MM-DD`，补零后的字典序与时间序完全一致。直接比较字符串，避免每筛一条记录做一次 `strptime`（`filter_records` 会被统计模块对全量记录反复调用）。

### 3.4 三级排序保证结果稳定

排序键 `(date, created_at, id)` 整体倒序，对应 README 6.4 的 `date desc, created_at desc, id desc`。`created_at` 统一 UTC 毫秒精度，字典序等于时间序；`id` 作为第三键，解决"同一天同一毫秒录入两条"时顺序随机的问题——没有它，翻页会出现同一条记录出现两次、另一条永远看不到。

### 3.5 `total` 是分页前的匹配条数

`total = len(ordered)` 在切片之前计算。`offset` 超出范围时 `items` 为空、`total` 仍是真实匹配数（前端据此显示"共 N 条"而不是"0 条"）。分页不能影响筛选条件，也不能影响统计（统计模块直接调 `filter_records`，不走 HTTP）。

### 3.6 路由是薄层，参数走白名单

`ALLOWED_PARAMS` 是白名单：拼错成 `startDate`、`category_id` 会返回 400 并定位字段，而不是被 Flask 悄悄忽略后返回全量数据。路由只读一次存储，把快照同时用于筛选和 total，避免两次读盘之间数据变化导致 `items` 与 `total` 不一致。

## 5. 已知限制

1. **同名校验参数只取第一个**。`?type=income&type=expense` 取 `income`，未做重复参数报错；如果老师追问，可改为检测 `len(request.args.getlist(name)) > 1` 直接 400。
2. **`id desc` 是字符串序**。UUID 字符串的字典序不代表生成时间序，它的作用只是让同一天同一毫秒的记录顺序稳定，不是"最新创建的在前"；真正的时序由 `created_at` 决定。
3. **筛选在内存里逐条比对**。个人账本量级足够；数据量大时应下推到存储层或数据库。
4. **不支持关键字搜索、导出**。README 14.3 的扩展需要 6 号新增契约参数、本模块加文本匹配，目前未实现。
5. **统计一致性依赖 5 号复用 `filter_records`**。如果 5 号另写一套筛选，就会出现"列表 3 条、统计 5 条"，这是联调时约定好的红线。

## 6. 演示时可以讲的三句话

- "列表和统计共用同一个 `filter_records`，所以同一组条件下列表条数和统计条数一定一致。"
- "排序是三级的：日期、创建时间、id，第三级专门用来让同毫秒记录的顺序稳定，翻页不会漏也不会重复。"
- "参数用白名单校验，`startDate` 这种驼峰写法会直接 400，避免用户以为筛选生效了、其实拿的是全量数据。"
